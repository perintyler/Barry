A Proposal

Agent Scope

A permission model for AI agent steps. Declarative, auditable, five minutes to write.

12 min read

AI agents are getting powerful. They can query your production systems, edit your codebase, open pull requests, file tickets, and run shell commands — all in a single pipeline. The ceiling on what an agent can do keeps rising.

But what an agent should do in a given step? That’s barely specified. Tool access is configured ad hoc, scattered across orchestration scripts, mixed in with prompts and control flow. There’s no shared way to declare, validate, or audit what a step is allowed to touch.

This matters because agent steps are not all equal. A step that reads Sentry issues is fundamentally different from a step that pushes code. But today, both get configured the same way — a list of CLI flags that a reviewer has to mentally parse to understand the blast radius.

The barrier to building agents has collapsed. The barrier to trusting them hasn’t.

01 — The Landscape

How we secure agents today

The industry has converged on a few approaches, each solving a real problem — but none solving the whole thing.

OS-Level Sandboxing

84%

Reduction in permission prompts with Claude Code’s sandbox. Kernel-level enforcement controls where an agent operates.

Can’t express “read Sentry issues but not create them.”

Identity & Authorization

IAM

Agents as non-human identities. OAuth tokens, scoped credentials, delegated permissions.

Right for prod, but heavy infrastructure. Doesn’t help within a pipeline.

Guardrails & Gateways

OPA

Proxy layers with policy-as-code. Detect PII leakage, prompt injection, unauthorized calls.

Like using Kubernetes to run a cron job.

Prompt-Based

93%

Auto-approved permission prompts in Claude Code’s classifier. Works surprisingly well.

Fundamentally soft. Prompt injection can route around it.

The gap: there’s no lightweight, declarative way to specify what an agent step is allowed to do — something between “kernel sandbox” and “full enterprise IAM.”

Permissions should be declarative and separate from logic.

When permissions are tangled into orchestration code, security review means reading every script. When they’re declared in a standalone file, a reviewer can understand what a step is allowed to do without reading how it does it.

This is the same insight behind IAM policies, OAuth scopes, and Kubernetes RBAC. The agent world just hasn’t caught up yet.

02 — The Concept

Agent Scope

An agent scope is a JSON file that declares what a single agent step is allowed to do:

agent-scope.json 
{
  "mode": "read",
  "tools": {
    "allow": ["mcp__sentry__*", "Read", "Grep", "Glob"]
  },
  "bash": {
    "enabled": true,
    "allow": ["git log", "git blame"]
  },
  "network": { "allow": ["*.sentry.io"] },
  "max_turns": 15
}

That’s the entire blast radius of the step, in one place. It lives alongside the prompt. It’s reviewed, versioned, and audited like code.

03 — The Model

Read and Write

Every tool, and every agent step, is classified as either read or write.

  • Read: Observes state without side effects. Querying Sentry, searching logs, reading files.
  • Write: Creates or modifies state. Editing files, creating issues, pushing branches.

A three-tier model — observe, create, mutate — is tempting. We rejected it. Is git commit create or mutate? Read/write is universally understood. Fine-grained control comes from the tool allowlist, not the mode.

The mode acts as a ceiling. A read-mode step cannot include write-classified tools. Misconfigurations get caught at validation time, not at runtime.

04 — Classification

Toolsets

Who decides whether search_issues is a read or a write? A toolset is a named collection with access mode classifications:

TypeScript 
const sentry: Toolset = {
  name: "sentry",
  tools: {
    "search_issues": "read",
    "get_issue_details": "read",
    "find_organizations": "read",
  }
};

Define the classification once. Share it everywhere. Toolsets decouple classification from naming — the tool’s own name maps to an access mode regardless of the MCP server prefix.

05 — Runtime

Scopes vs. Grants

The scope is the policy — what you want. The grant is the permission set — what you get. The scope is authored by the developer. The grant is computed at runtime.

TypeScript 
interface Grant {
  tools: string[];
  bash: BashScope | null;
  network: NetworkScope | null;
  maxTurns: number;
  mode: "read" | "write";
}

You can define a scope that references tools that don’t exist yet — the grant simply won’t include them.

Classification Resolution

Not every tool comes with a classification. Agent-scope uses a layered strategy:

  1. User-provided — highest priority. Users know their own tools.
  2. MCP annotations — readOnlyHint and destructiveHint.
  3. Toolsets — built-in and user-provided mappings.
  4. Conventions — get_*, list_* → read. create_*, delete_* → write.
  5. Default → write — deny-by-default is safer than allow-by-default.

You don’t need perfect classification upfront. A layered fallback with a safe default handles the long tail.

06 — Special Cases

Bash is special

Classifying bash as “read” or “write” is meaningless. bash can curl, rm -rf, git push --force, or cat /etc/passwd. It’s a meta-tool.

agent-scope.json 
{
  "bash": {
    "enabled": true,
    "allow": ["git log", "git blame", "git show"],
    "deny": ["rm", "git push --force"]
  }
}

Commands are validated by parsing compound commands into segments, checking deny (always wins), then allow (prefix match), rejecting anything uncovered. Deny-by-default.

Network Scope

Read mode permits GET, HEAD, OPTIONS only. Write mode permits all methods. Domain scoping is optional. Like bash scope, this is a validator — the runner enforces it.

Why “Scope”

Sandbox implies runtime isolation. Harness overloads existing terminology. Scope is simple and well-understood — OAuth uses scopes for granting specific permissions. Same idea applied to agent steps.

07 — Conclusion

Why it works

  • Permissions are visible at a glance, separate from logic
  • Tool classification is shared and consistent across agents
  • Framework-agnostic — any agent runner can use it
  • Bash and network access are explicitly scoped
  • New MCP servers work out of the box via conventions
  • The mode ceiling catches misconfigurations early

The bottom line: a scope file takes five minutes to write and makes every step auditable.

Agent Scope is an open-source package for declaring, validating, and enforcing AI agent permissions.
