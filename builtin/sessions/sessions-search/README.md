# sessions-search

Semantic search over every past session. Finds conversations by **meaning**, so
"why did the deploy break" reaches a session about a rolled-back migration even
though it shares no words with it.

Embeddings are generated by a local model, so the index costs nothing and no
session text leaves the machine.

## Setup

```bash
brew install --cask ollama
ollama pull nomic-embed-text
```

Then build the index over the existing archive — once, ~12 minutes for 90k
messages:

```bash
BARRY_EMBED_BACKFILL=1 npx tsx ../api/src/jobs/embed.ts
```

After that the `embed` job keeps it current every 15 minutes.

## Searching

The `search_messages` tool takes a natural-language question:

> search_messages("what was the fix for the CI failure")

Results are **hybrid**. Semantic hits are interleaved with the existing word
search rather than replacing it, because the two are good at different things:
word search still wins for an identifier, an error string, or a partial word
like `postg`, while semantic search wins for a paraphrase. Each result is
labelled `[meaning]` or `[words]` so it is clear which engine found it.

If Ollama is not running, search degrades to word-only and **says so**. A
quietly narrowed result set would look like a working index returning nothing.

## What gets indexed

Message text from both sides of the conversation. Indexing only the user's
messages was the original plan and measurement showed it was wrong: for
questions like "what did we decide about the schema", assistant messages took
8 of 8 top-1 results, and on a role-balanced pool 26 of 40 top-5 slots against
a 20/20 chance baseline. Your messages ask the questions; the assistant's hold
the answers.

Tool calls are excluded. They are structured payloads rather than prose, and
the paths and commands in them are what word search already handles well.

## How the job keeps up

Each session carries a watermark — the highest message sequence already
embedded — in `sessions.metadata.embedding_watermark_seq`. A tick counts
messages per session in one batched query and only reads the sessions that
moved, so a quiet tick makes no model calls at all.

The watermark advances past messages that were **skipped**, not just embedded
ones. Tool traffic is most of the table, and a watermark that only moved on
success would re-read all of it every tick forever.

## Storage

Vectors live in the shared `embeddings` bag (`embeddings.db` in its data directory) under the
`session-messages` collection, so the index survives this bag and any other bag
can read it.

## Environment

| variable | meaning |
|---|---|
| `BARRY_EMBED_MODEL` | Embedding model (default `nomic-embed-text`) |
| `BARRY_EMBED_MAX_PER_TICK` | Ceiling on messages embedded per tick (default 2000) |
| `BARRY_EMBED_BACKFILL=1` | Index the whole archive instead of the recent window |
| `BARRY_VECTORS_DB` | Override the vector store location |
