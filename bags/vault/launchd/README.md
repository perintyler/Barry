# Vault LaunchDaemon

Composes and installs the root-owned LaunchDaemon that runs the vault as
`_barryvault`. See `../CUTOVER.md` for where this fits in the overall
sequence, and `../README.md` for why the isolation is shaped this way.

## Generate the plist

```bash
cd bags/vault
pnpm run build                        # produces dist/server.mjs
pnpm exec tsx launchd/generate-plist.mts
```

Writes `launchd/com.barry.bag.vault.api.plist.generated` — gitignored
(`*.generated`), since it embeds `JWT_SECRET` and `VAULT_CLIENT_SECRET` in
plaintext, resolved from the repo's `.env` at generation time. **Delete this
file after installing it** — it is not meant to persist on disk once the
plist is in `/Library/LaunchDaemons`.

Running from a worktree: `.env` is deliberately per-checkout, not copied into
worktrees. Point at the real one with `BARRY_ENV_FILE`:

```bash
BARRY_ENV_FILE=/path/to/main/checkout/.env pnpm exec tsx launchd/generate-plist.mts
```

## Install (needs sudo — see the comment inside the generated plist)

The plist's own header comment carries the exact install sequence — read it
before running anything, since it names the paths this generator assumes
(`/usr/local/libexec/barry-vault`, `/usr/local/var/barry-vault/{logs,run}`).

In short: bundle → install root-owned, not writable by the invoking user →
create `_barryvault`-owned log/socket directories → install the plist itself
(0600, root-owned — it carries secrets) → `launchctl bootstrap system`.

## Why this isn't generated by `scripts/launchd/setup`

That script deliberately refuses to emit any service declaring `user:` and
tells the operator to install it as a LaunchDaemon by hand — creating a
system daemon needs root, and `setup` runs unattended on every `barry pack`.
This script reuses its env-resolution logic (`resolveServiceEnv` from
`@barry-rocks/bags`) rather than reimplementing `.env` parsing, but the
plist assembly is bespoke: a LaunchDaemon needs `UserName`/`GroupName`
fields a per-user LaunchAgent never has, and its working directory / log
paths must live somewhere `_barryvault` can write — nothing under the
invoking user's home is eligible.

## A gap this surfaced, worth knowing about

`bag.yaml`'s `env:` block declares `JWT_SECRET` etc as its `.env`-sourced
variable names — matching what the running server actually reads
(`process.env.JWT_SECRET`) — but `resolveServiceEnv`'s `.env` source reads
that *same* name from the environment `setup` runs under, and the repo's
`.env` only carries the docker-compose convention `BARRY_VAULT_JWT_SECRET`
(interpolated into the container's `JWT_SECRET` by `compose.yml`). Nothing
in `packages/bags` does that rename outside a container boundary.

This was invisible until now because the entry (then named `vault-bag`) had
been `disabled: true` in `config/bags.builtin.yaml` since it was written —
this generator was the first thing to actually exercise that code path.
(The registry key is now `vault`, enabled — see CUTOVER.md step 5. The
`vault-bag` name was a temporary disambiguation while both it and the now-
retired `vault:` remote entry needed to coexist.) `generate-plist.mts` works
around it with an explicit rename table rather than patching the manifest
schema, since the manifest's env-var semantics (one name meaning both "read
from .env as X" and "expose to the process as X") need a real design
decision this cutover doesn't need to make. If `bag-items.mts` is ever
pointed at this bag for real, it will hit the exact same failure.
